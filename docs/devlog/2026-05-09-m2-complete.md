## 这一里程碑的关键决定

### 1. 切换到 Subagent-Driven Development

M1 时是主代理一把抓。M2 一开始就改成"plan → 派发子代理 → 主代理只裁决 review"。**好处明显**：

- 每个 task 都独立 commit，回滚便宜
- spec reviewer 反复发现"plan 中的代码片段已经过时"问题 —— 比如 plan 说 `import 'package:drift/drift.dart';` 但实际代码不需要（unused_import 会被 lint 拦），implementer 自动调整后标 `DONE_WITH_CONCERNS`，主代理裁决放行
- code-quality reviewer 在 Task 10 抓到 `FutureBuilder<void>` 副作用反模式 + 缺错误处理，主代理立刻补 polish commit（`a298194`），让随后的 Task 12 直接复用正确模式

### 2. Plan 顺序重排：UI 页面前置，路由最后

原 plan Task 8 是路由重接，跟在 service 后面。但路由切到 `DeckListPage` 时该页还没写，会编译失败。我们决定把所有 UI 页（Task 9-12）写完后再统一路由（`m2-t8b`），保证**每个 commit 都可编译可启动**。

### 3. Stream-first 的 reactivity 修正（Task 11）

最初 `deckByIdProvider` 是 `FutureProvider`，结果 `DeckEditPage` 改名后回到 `DeckDetailPage` 不会刷新，因为 future 已 cache。code reviewer 当场抓到，立刻：

1. 给 `DecksDao` 加 `Stream<Deck?> watchById(int id)`
2. `deckByIdProvider` 改 `StreamProvider.autoDispose.family`
3. 加测试

写完测试后第二轮 review 又发现：**新加的 reactivity 测试本身没在测 reactivity** —— 它用了两次独立订阅，即使方法是非响应式的也会通过。修正成 `expectLater + emitsInOrder` 的单订阅模式（commit `0ff21d2`）才真正卡住"流必须 emit 第二次"这个不变量。

这是本次 M2 最有价值的两个问题之一。

### 4. CardEditPage 直连 databaseProvider（架构小破窗）

`CardEditPage` 编辑模式下需要"按 cardId 取 card + 它的 note"，目前没有 `CardService.getCardForEdit`，pages 直接 `ref.read(databaseProvider)` 取 DAO。**v0.1 容忍**，写在 cleanup TODO 里：M5 加 cloze 时如果还需要类似查询，再统一抽 `CardService` 方法。

## 遇到的问题与解决

### 1. Task 1：plan 里的 import 是 dead code

**现象**：plan 里 `seed.dart` 顶部写了 `import 'package:drift/drift.dart';`，但 seed 函数体只用 `NoteTypesCompanion.insert` 和 `DateTime`，drift 的 `Value` 类用不到。lint 报 `unused_import`。
**解决**：implementer 删了这个 import。**收获**：plan 里的 code snippet 是大致结构，不应该按字面照抄，要按实际依赖裁。

### 2. Task 1：`build_runner --delete-conflicting-outputs` 已废弃

**现象**：Plan 写了 `--delete-conflicting-outputs`，但当前 `build_runner` 把这个 flag 当未知参数忽略（codegen 仍然成功）。
**解决**：后续 task 全部去掉这个 flag。

### 3. Task 4：`require_trailing_commas` 与单行参数列表

**现象**：plan 里测试代码有 `CardsCompanion.insert(noteId: 1, deckId: 1, due: 0, createdAt: 0, updatedAt: 0)` 这种单行写法，触发 lint。
**解决**：implementer 自动重排成多行 + 尾逗号。

### 4. Task 10：`FutureBuilder<void>` 反模式 + 缺错误处理

**现象**：DeckEditPage 用 `FutureBuilder<void>` 触发"加载已有名字到 controller"的副作用，每次 rebuild 都会 new 一个新 future；同时 `_onSave` 没 try/catch，失败会让 `_saving = true` 永远卡住成"僵尸表单"。
**解决**：refactor commit `a298194` 把 load 移到 `initState() + Future.microtask`，给 save 加 `try/catch + SnackBar` 并 finally 复位 `_saving`。**Task 12 直接照新模式写**，避免重复修。

### 5. Task 11 的测试反复修了两次

**现象**：第一版 `watchById` 测试用 `dao.watchById(id).first` 取一次，更新后再取一次 —— 跟"是否真响应式"无关，DAO 即使是非 stream 方法也能过。
**解决**：commit `0ff21d2` 改用 `expectLater(stream, emitsInOrder([...]))`，单订阅看到 update 必须 emit 第二次才通过。

### 6. router rewire 后旧 HomePage 引用残留

**现象**：删 `HomePage` 文件后差点漏删 import 和 router 中的 `GoRoute('/', HomePage())`。
**解决**：implementer 一把删干净，subagent review 阶段 `flutter analyze` 0 issues 才放行。

## 反思与心得

1. **subagent 流程值回票价**。最有价值的两次都是 reviewer 抓的：DeckEditPage 反模式 + watchById 测试假阳性。如果是主代理一把过，这两个都会埋进去。
2. **plan 不是合同，是脚本注释**。多个 task implementer 偏离 plan 的 import / 单行写法 / cli flag —— 都是为了过 lint。这是健康的。Plan 写得过细反而是负担。
3. **Stream-first 在 Riverpod 里要 default**。除非数据真的是单次拉取（比如 build 信息、配置常量），列表/详情都应该 `StreamProvider`。这次的 staleness 问题就是凭"先选 FutureProvider 再升级"出的。
4. **测试要测不变量，不是测代码路径**。第一版 `watchById` 测试只是把代码跑了一遍，没有定义"如果不响应式就要失败"的不变量。下次写 stream 测试直接想"哪种实现会让这个测试失败"。
5. **每个 task 一个 commit + 主代理只看 review，效率反而比一把抓高**。看起来 overhead 大，但因为 reviewer 能拦住的问题越早拦住越便宜，而且每个 commit 描述清晰，将来 rebase / cherry-pick 成本接近 0。
